# 社区信息流 SQL 优化与同环境对照

日期：2026-11-03。代码基线 bf18ec1。本版保留一次 D1 请求及原有分页协议，将整表评论分组改为只汇总当前页帖子的评论。窗口总数仍在分页之前计算，DTO 转换和排序字段白名单沿用原实现。没有执行生产索引或生产写入。

## 同环境结果

本机 SQLite 3.53.4，单个内存数据库，合成 10,000 条帖子、100,000 条评论，含软删除、无点赞和多语言字段。每组先预热，再交替执行前后查询各 9 次，报告中位数。索引场景在同一索引状态下比较 SQL 前后；没有拿无索引旧 SQL 对比有索引新 SQL。结果是数据库本地执行及结果读取时间，不含 D1 HTTP、跨地域网络或 App 渲染。

| 索引 | 页大小 / 页码 | 修改前 ms | 修改后 ms | 减少 |
| --- | --- | ---: | ---: | ---: |
| 无 | 5 / 0 | 44.519 | 32.804 | 26.3% |
| 无 | 10 / 1 | 47.944 | 37.235 | 22.3% |
| 无 | 50 / 20 | 52.423 | 42.390 | 19.1% |
| 无 | 1000 / 0 | 60.854 | 55.195 | 9.3% |
| 有 | 5 / 0 | 36.421 | 31.368 | 13.9% |
| 有 | 10 / 1 | 33.310 | 29.038 | 12.8% |
| 有 | 50 / 20 | 36.547 | 30.690 | 16.0% |
| 有 | 1000 / 0 | 44.189 | 38.667 | 12.5% |

测量范围内均有改善，不承诺真实生产数据分布下相同收益。索引场景中查询计划能按当前页 post_id 搜索评论覆盖索引；无索引仍需扫描评论，但减少了无关帖子的分组。窗口总数仍需遍历符合条件的帖子，因此不是恒定时间分页。原始逐次耗时与 EXPLAIN QUERY PLAN 见 benchmark-results.json。

## 一致性与回归

136 组 SQL 结果对照通过：四种允许的排序字段、升降序、多种分页尺寸、深分页及超出末页，并补测相同排序值、全删除和空表。逐行逐字段比较总数、点赞、评论、删除标记和翻译字段。空页时原实现返回总数零的行为保留；相同排序值的全局稳定顺序原接口未定义，本轮不增加新排序协议。

独立编译全部主代码完成；504 个路由断言、504 次模拟依赖控制器请求、21 项缓存恢复、5 项观测、10 项上一版性能缓存及 2 项压缩测试通过。504 条模拟响应记录与历史基线一致。这里只算隔离回归，不代表真实数据库和手机端到端业务验收。

## 音乐分页与索引

音乐候选 create_at 索引在 10,000 条合成记录、首页 10 条时，本地中位数由 1.27ms 降至 0.01ms，返回结果一致。尚未核验生产现有索引，候选脚本 candidate-indexes.sql 未挂入自动迁移，也未在线执行，因此音乐生产优化尚未落地。评论索引在仓库旧建议中已有定义；目标数据库若已有等价索引，不应重复创建。

## 复跑与部署边界

在后端仓库根目录执行：

```sh
python3 docs/qa/quittr-sql-optimization-2026-11-03/benchmark.py
python3 docs/qa/quittr-backend-reliability-2026-11-03/run_regression.py --output /tmp/quittr-sql-new-run
```

benchmark.py 只连接内存 SQLite，会更新本目录 benchmark-results.json；会核对实际 Java SQL 与 after.sql 一致。before.sql 为修改前语句快照。回归脚本不加载整个生产应用，压缩用例仅监听本机随机端口。

正式上线前仍需在目标 D1 测试环境核对版本支持、真实数据分布和查询计划，再验证实际 HTTP 耗时、统计一致性及资源消耗。此报告不能替代该阶段。中国社区信息流此前公开样本约 570ms，不能把本地 SQL 减少的比例直接套在这个端到端数字上。

本轮仅本地提交 SQL 改动和验证材料，不推送、不部署；原有歌词、歌曲导入、特效等未提交改动保持原样。
